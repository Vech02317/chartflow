# 任务:从源码抽取类与关系 → `figs/<id>.json`(类图)

## 输入(按优先级取其一)
1. 类定义源码(Java / Python / C# / TypeScript 等)
2. 接口定义
3. 正文里对类结构的描述(仅在无源码时)

## 输出
一个 JSON 文件,保存为 **`figs/<图清单里的 id>.json`**,严格符合 `contract/class.schema.json`。
**只输出 JSON 内容**,不要解释。

## 抽取规则
1. **只画有业务含义的类**。工具类、常量类、异常类一般不入图,除非论文正文强调。
2. `attributes` / `methods` 只写**名称或签名**,不写类型细节:
   - 属性:`"title"` 或 `"title: str"`
   - 方法:`"borrow(reader, book)"` —— 带括号和参数名,不写返回类型
3. 只保留**有意义的成员**:省略 `__str__`、getter/setter、`__init__` 之类样板(除非论文强调)。
4. `stereotype`:抽象类填 `abstract`,接口填 `interface`,枚举填 `enum`,普通类填 `class`。
5. 关系判定(`kind`):
   - 子类继承父类 → `继承`
   - 成员是另一个类的**组成部分**(生命周期一致,如 Body 与 Head) → `组合`
   - 成员是另一个类的**集合**但可独立存在 → `聚合`
   - 单向持有引用 → `关联`
   - 只在方法参数/局部变量里出现 → `依赖`
6. 拿不准的关系**不要写**,在给人类的回复里单列"待确认"。
7. 类数量超过 15 个时,**只画核心类**并在回复里说明省略了哪些(密集类图 dot 布局会很难看,宁可少而准)。

## 自检
- [ ] 每个 `class.name` 都是源码里真实的类名
- [ ] 每条 `relation.from` / `relation.to` 都能在 `classes` 里找到
- [ ] 没有把 getter/setter/`__str__` 这类样板方法写进去
- [ ] 类数 ≤ 15(超过就精简)

## 完成后
回报"待确认"清单与"已省略的类"。
