# 任务:抽出一个实体的属性图数据 attr.json

## 你的角色
产出**一个实体**的陈氏(Chen)属性图数据,严格符合 `contract/attr.schema.json`。
**一张图只画一个实体** —— 论文里有几个实体就出几条记录、几张图,不要把多个实体塞进一张。

## 输入
- 该实体的 models 代码 / 建表语句(**源头真相**)
- 论文正文里对该实体的描述 —— 只作补充;**与源码冲突时以源码为准**

## 图型说明
中央矩形是实体,周围椭圆是属性。属性画成什么样,由 `kind` 决定:

| `kind` | 画法 | 什么时候用 |
|---|---|---|
| `pk` | 椭圆内属性名下**加下划线** | 主键。**必须有且只有一个** |
| `multi` | **双椭圆** | 一个实体可取多个值,如一个读者登记多个"联系电话" |
| `derived` | **虚线椭圆** | 由别的属性算出来、不单独存,如"年龄"由出生日期推算 |
| `normal` | 普通椭圆 | 其余(默认值,不写 `kind` 就是它) |

## 规则(必须遵守)
1. **`label` 用中文属性名**(取 `verbose_name` / 建表注释);**不要**把英文列名画到图上。
   `name` 填英文列名,只用于追溯出处。
2. **`pk` 有且只有一个**。Django 没显式写主键时,主键就是隐含的 `id`,label 取"XX编号"
   (如"读者编号");自建主键照源码写。
   **若这个 label 与该实体其它属性的 label 撞车**(如某字段的 `verbose_name` 恰好就叫"用户编号"),
   主键改用"XXID"或"XX主键" —— 同一个框里不能有两个同名椭圆。
3. **不画联系**。外键(`ForeignKey`)和多对多(`ManyToManyField`)**都不画** ——
   它们是**实体之间的联系**,归整体 ER 图管,不属于单实体的属性图。
   `ManyToManyField` 尤其不要当成"多值属性":多值属性指同一个实体自己就能存多个值,而多对多
   指向的是另一个实体,是联系。
   正文或数据字典里若坚持要画,让人来定,不要自己加。
4. **不编造**。源码/建表语句里没有的字段一律不写进 `attributes`;正文里提到、源码里没有的,
   列进"待确认",**不要**先画上。
5. 属性只放**不可再分的数据项**。像"规格"这种还能再拆的,拆成多个属性。
6. 实体中文名取 `Meta.verbose_name`,没有就用类名。

## 常见歧义点(照此办,不要自己定)

1. **继承来的字段**(如 `class User(AbstractUser)`)——**可自行取舍,但必须逐条列明**。
   父类字段确实会建到表里,画进去不算编造;但属性图只有一个实体,字段一多椭圆就挤爆
   (实测:用户属性图 10 个属性 → 376×373pt;并全 16 个 → 需缩到 84%)。
   所以:挑业务上读得懂的并入(至少 `username` / `password` 这类核心字段),
   **然后在"待确认"里逐条写出「并入了哪些」「省略了哪些」**。不能静默。
   `ManyToManyField`(如 `groups` / `user_permissions`)**一律不并入** —— 规则 3 说了,那是联系。

2. **属性 `label` 里的括号说明**(如"文件大小(字节)""正文(Markdown)")
   是 `verbose_name` 原文的一部分,**照抄,不要自己删**。嫌太长由人拍板精简 —— 你删了就是改数据。

3. **主键 label 撞车**:见规则 2。

4. **`label` 的来源**。优先 ① 源码里的中文(`verbose_name` / 建表注释 / 中文注释)——
   这种**不用报**。源码里没有中文时,才会去 ② 论文的表结构备注或正文里取;
   而**论文的列名常常和源码对不上**(实测踩过:论文写 `xuesheng_username`,源码是 `username`),
   那时你是**跨两套列名做人工对齐**,那已经是判断了 ——
   **"论文与源码列名不一致"这件事本身、以及你按什么对齐的,都要写进"待确认"**。
   论文压根没有的字段(`grade` 这种),label 只能 ③ 意译 ——
   **逐条列出是哪些属性**,不要并进别的条目。
   **意译出来的中文和抄来的一样可信,人不看这份清单就分不出来。**
   判断标准一句话:这个中文名,**人能拿它对着源码逐字核吗**?不能,就必须报。

## 输出
只输出 JSON,保存为 `figs/<id>.json`,不要写解释。

## 自检(输出前逐条核对)
- [ ] `attributes` 里有**且只有一个** `kind: "pk"`
- [ ] 每个属性都有中文 `label`
- [ ] 没有把外键 / 多对多字段当成属性画进来
- [ ] 源码里没有的字段,一个都没画
- [ ] 主键的 `label` 和该实体其它属性**不重名**
- [ ] 有继承的实体(如 `User(AbstractUser)`),在"待确认"里**逐条写了**并入/省略了哪些父类字段
- [ ] 论文与源码列名不一致时,已在"待确认"里写明"不一致"和**对齐依据**
- [ ] 意译来的属性 `label`(源码和论文里都没有中文的)**已逐条列出**

## 完成后(不能省)

**把"待确认"清单写进 `figs/<id>.待确认.md`**(`<id>` 是本图 id),再在对话里简述一遍。
属性图最常出的两个错,正是**多画**和**漏画**字段 —— 这张图是给人对着数据库核对的,
漏一个字段就等于交了一张假图。所以继承字段的取舍、主键改名、**每个属性 `label` 的来源**
(见「常见歧义点」第 4 条)之类,**都必须落盘**。
真的没有要人拍板的,**就写"无"**。

`build.py` 会把各图的这份文件汇总成 `out/待确认.md` 交给人类。
