# 任务:从源码抽取实体关系 → `figs/<id>.json`(ER 图)

## 输入(按优先级取其一)
1. 实体类源码(Django / SQLAlchemy / JPA 等)
2. 建表 SQL(DDL)
3. 数据字典文档

## 输出
一个 JSON 文件,保存为 **`figs/<图清单里的 id>.json`**,严格符合 `contract/er.schema.json`。
**只输出 JSON 内容**,不要解释。

## 抽取规则
1. **源码为准,正文只补充**:字段名、类型、外键只从代码或 SQL 取;论文正文与代码冲突时**以代码为准**。
2. `entity.fields` **只放非外键列**(含主键);外键写进 `relation.fk_field`,不要重复成字段。
3. 关系方向:`from` 是**"一"侧**,`to` 是**"多"侧**,`cardinality` 写 `1:N`。
4. `name` 用代码里的原名(如 `BorrowRecord`);`label` 用中文(取 `verbose_name` / SQL comment;没有就意译)。
5. **不编造字段**。有拿不准的字段或关系,**不要写进 JSON**,而是在给人类的回复里单列一条"待确认"。
6. 纯连接表(只有两个外键、无业务字段)——省略成一条 `N:M` 关系,不单列实体。
7. 主键字段带 `"pk": true`(Django 的 `id` 即使没显式声明也算)。

## 常见歧义点(照此办,不要自己定)

下面这几处,源码里**查不到唯一答案**。**照这里的口径办**,并把你的实际处理写进"待确认" ——
不要自己挑一个就当没这回事。

1. **继承来的字段**(如 `class User(AbstractUser)`)——**可自行取舍,但必须逐条列明**。
   父类字段确实会建到表里,画进去不算编造;但全部并入会让图明显变小
   (实测:用户属性图 10 个属性 → 376×373pt;并全 16 个 → 需缩到 84%,继承越深越糟)。
   所以:挑业务上读得懂的并入(至少 `username` / `password` 这类核心字段),
   **然后在"待确认"里逐条写出「并入了哪些」「省略了哪些」**。不能静默。
   `ManyToManyField`(如 `groups` / `user_permissions`)**一律不并入** —— 那是联系,走 `relations`。

2. **关系上的中文 `label`**:取外键的 `verbose_name`,**去掉"人 / 者 / 的X"这类指代后缀**,
   得到动词短语(如 `verbose_name="接收人"` → `"接收"`);没有 `verbose_name` 就用动词意译。
   同一对实体之间有多条语义不同的关系时,**label 必须能区分**(如"发起" / "被加")。
   拿不准的写进"待确认",让人类给固定叫法。

3. **`N:M` 关系的 `from` / `to` 方向**:N:M 既没有"一"侧也没有"多"侧,规则 3 管不到它,
   改用——**`from` 是声明 `ManyToManyField` 的那一端**
   (如 `PersonalNote.tags = ManyToManyField(Tag)` → `from: PersonalNote, to: Tag`)。可对着源码核。

4. **`table` 名**:源码有 `Meta.db_table` 就照抄;**没有**则按 Django 默认命名
   (`<app>_<模型名小写>`)推断,并**在"待确认"里注明这是推断的**。不要默默写一个看似确定的表名。

5. **外键写成 `settings.AUTH_USER_MODEL` 时**:按项目 `settings.py` 里 `AUTH_USER_MODEL` 的实际取值连。
   看不到 settings 时,按常见的 `accounts.User` 连,**并列入"待确认"请人确认** —— 这里连错,
   所有用户外键一起错。

6. **多态 / 松散引用**(如 `Todo.target_id` 存"书ID或用户ID"、但源码里没有 `ForeignKey`):
   **图上画不出这种指向,不要硬连成外键** —— 列进"待确认",让人决定怎么表达。

## 模块划分(只在实体多时做)

实体太多时,一张紧凑版会宽到插不进 A4。给实体标上 `module`、顶层写上 `modules`,
引擎就会**自动多产出几张按模块拆的图**(`out/<id>_mod_<模块>.png`),零缩放就能插论文。

**要做**:本图实体数 **≥ 8**。
**不要做**:实体数 **< 8** —— 实测 4 实体紧凑版只有 322×251pt,本来就装得下;硬拆只会让
论文里图数变多、显得零碎。**没有"为了显得完整"而拆的道理。**

### 怎么写
- 顶层 `modules`:每项 `{name, label, title}`。`name` 是模块标识(只许小写字母数字下划线),
  `label` 是论文里的中文模块名,`title` 是**要印在图上的图题**,如 "书籍模块 E-R 图"
  —— **自己写完整,不要让脚本去拼**。
- **`name` 怎么取**:优先取**源码里可核证的那个 app 名** —— `Meta.db_table` 的前缀,
  或外键字符串引用里的前缀(如 `ForeignKey("venue.VenueSlot")` 里的 `venue`)。
  **源码不是包结构、只有一堆平铺的 `*_models.py` 时,不要只看文件名** ——
  文件名可能缩写过(实测踩过:文件叫 `admin_models.py`,而真实 app 是 `admin_panel`)。
- 每个实体加 `module`,取值必须是 `modules` 里出现过的 `name`(写错会被验收拦下)。
- 参考样例:**`samples/campus/figs/fig1.json`**(3 模块 12 实体,照抄它的写法)。

### 模块边界按什么划
- **默认按源码** —— 实体在哪个 app / 包 → 哪个模块。这条可对着源码核,最不容易错。
- **论文正文的功能模块划分与源码不一致时,以论文为准** —— 图要跟论文对得上。
  但**必须**在"待确认"里写明:"源码的 app 划分是 X,本图按论文正文分成 Y"。
- 模块边界拿不准、或论文要求一个实体同时出现在两张模块图里 —— **不要自己编**,回报人类。
  本流水线只支持"一个实体一个模块"的分区。

### 两件必须说清的事
- **不用写外部实体,也不要为外部实体编字段。** 不在本模块的实体会由**引擎**自动画成
  虚线引用框(只写实体名、不列字段)。
- **所以你仍然要把全部实体的字段都写全。** 虚线框不是少写字段的理由 —— 漏字段就是交了一张假图。
  同理,**关系也要写全**:引擎按"关系的 `to` 端(外键所在端)属于哪个模块"把它分给对应那张图,
  保证每条关系都出现在某一张模块图上,一条不丢。

## 自检
- [ ] 每个 `entity.name` 都是源码里真实存在的类名/表名
- [ ] 每条 `relation.from` / `relation.to` 都能在 `entities` 里找到
- [ ] 每个实体有且仅有一个主键
- [ ] 没有把外键列写进 `fields`
- [ ] 实体数 ≥ 8 时写了 `modules`,且**每个实体都标了 `module`**、取值都在 `modules[].name` 里
- [ ] 每个模块至少 1 个实体,没有为凑数而设的模块
- [ ] `module` 与源码的 app/包名对得上(对不上说明理由,写进"待确认")
- [ ] 有继承的实体(如 `User(AbstractUser)`),在"待确认"里**逐条写了**并入/省略了哪些父类字段
- [ ] 每条 `N:M` 关系的 `from` 都是声明 `ManyToManyField` 的那一端
- [ ] `table` 若是推断来的,已在"待确认"里注明

## 完成后
把"待确认"清单回报给人类(这一步不能省:验收脚本只能证明图和契约一致,证明不了契约和事实一致)。
若做了模块划分,一并说明**模块划分的依据**(源码的哪个 app / 论文的哪一节)。
